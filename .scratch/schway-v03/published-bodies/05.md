## What to build

A user enables a local TypeScript extension and the agent executes its custom tool through the existing scheduler and validation path. Scope: sections 27–29, 50, 58–59, 79, 90.

## Existing behavior and problem

The existing tool registry already accepts JSON Schema, compiles validators once, rejects duplicate names and exposes parallel/exclusive scheduling. The native ToolContext carries workspace, AbortSignal and streaming output. The missing piece is explicit executable extension loading and a public registration entry point.

## Prerequisite contract

No blockers. Reuse existing tool/runtime contracts and introduce only the small public registration seam needed for this consumer.

## Required behavior and decisions

1. Support repeatable --extension <local-module> in interactive and headless startup, preserving explicit argument order. Resolve relative module paths from the primary canonical workspace root; use canonical module identity to reject duplicate enablement.

2. Provide a documented Schway extension entry that receives a capability-limited context with tool registration. Ship an importable public contract from the single package so a packed/installed consumer can typecheck without reaching into private source modules.

3. Invoke extension registration before taking tool definitions for the first model request. JSON Schema remains the public schema type; TypeBox is optional for extension authors.

4. Execute registered tools through the existing validation, AbortSignal, output handling and scheduler. The tool's declared execution mode, not its origin, determines concurrency and barriers. Define and enforce a bounded model-facing result policy for extension returns.

5. Treat extension initialization as atomic: registrations from a module that throws or registers an invalid/duplicate tool must not remain partially active. Fail startup actionably with extension identity; interactive recovery may return to a usable setup state.

6. Disabled or unmentioned modules execute no code. Do not scan dependencies and guess which packages are extensions. Executable extensions are explicitly trusted code; this feature does not claim sandboxing.

7. Preserve core ownership. Extensions register supported capabilities, not replacement loops, sessions, compaction engines, models or schedulers. Public contracts must not require OpenTUI or provider SDK types.

## Scope boundary

Explicit local loading and custom tools. Commands, observers, prompt hooks, package discovery and package installation are separate surfaces.

## Implementation constraints

- Use Bun and TypeScript. Run `bun run typecheck`; run `bun test` for behavior changes. Deterministic checks use scripted models, protocol fixtures and temporary filesystems rather than paid APIs.
- Schway owns the loop, session engine, context/compaction and tool scheduling. Provider SDKs are protocol clients with automatic retries disabled; core contracts use native conversation types.
- Keep core independent of OpenTUI and provider wire types. Headless execution must not load the TUI; only selected providers and explicitly enabled executable extensions load.
- Resolve tool-relative paths from the canonical primary workspace root (nearest Git root, otherwise launch cwd). Keep runtime events separate from durable semantic session records.
- Document newly exported functions/types with a one-line TSDoc contract. Preserve bounded model-facing output, exactly one result per accepted call and existing credential redaction.

## Verification scenarios

| Scenario | Observable result |
| --- | --- |
| Local TypeScript extension | Installed/headless fixture registers a custom tool and completes a real model → tool → model turn. |
| Scheduling/validation | Invalid arguments never execute; parallel/exclusive declarations and cancellation are honored. |
| Registration failure | Duplicate or invalid tool and thrown initialization leave no half-installed capabilities. |
| Lazy loading | A marker in an unenabled extension is never executed; headless loads no OpenTUI. |
| Package boundary | Public types resolve from a packed consumer; no private path imports are needed. |

## Acceptance criteria

- [ ] Provide a small importable extension entry contract and tool registration API, with one-line contract docs and a runnable example.
- [ ] Load only explicitly enabled local modules in deterministic order; support the local extension CLI option in headless and interactive modes.
- [ ] Reuse JSON Schema registration, validation, parallel/exclusive scheduling, bounded results and cancellation; do not require third-party TypeBox.
- [ ] Duplicate names, unsupported schemas and load failures identify the extension and leave a usable failure state.
- [ ] No replacement of agent/session/context/model/scheduler internals; disabled extensions incur no module execution and headless remains TUI-free.
- [ ] An isolated local extension fixture completes a custom-tool conversation through the real loop. Replace obsolete extension absence guards while preserving lazy-load tests.
- [ ] All required behavior and verification scenarios above are covered, including failure/cancellation cases relevant to this slice.
- [ ] User-facing commands/configuration and public contracts introduced by this issue are documented with a runnable example where applicable.
