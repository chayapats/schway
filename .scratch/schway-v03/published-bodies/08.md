## What to build

Extensions can modify or deny a requested tool operation and transform its supported result through beforeTool and afterTool hooks while retaining tool safety and session guarantees.

## Existing behavior and problem

The existing executor validates each model tool call, and the scheduler groups parallel calls around exclusive barriers. Local extensions can register capabilities. Add beforeTool/afterTool interception without losing the invariant that every accepted call has exactly one terminal result.

## Prerequisite contract

Requires the extension runtime's registration, load order and identity. Tool definitions already expose JSON Schema, execution mode, execute(input, context), bounded content and optional details. Scheduler and durable history remain Schway-owned.

## Required behavior and decisions

1. Validate the original requested tool name and arguments against the registered definition before invoking beforeTool. Unknown tools and invalid model arguments retain their ordinary bounded tool-error behavior.

2. beforeTool hooks form a waterfall in extension load order. They may replace arguments or deny execution with a reason; tool-call ID, selected tool name, schema and declared scheduling mode are immutable.

3. Validate transformed arguments again before tool execution. Revalidation failure, denial or hook exception settles the call as an error and never invokes the tool.

4. Run hooks inside that call's existing scheduling slot. Exclusive barriers cover the full hook/execution sequence; parallel calls may have independent hook waterfalls concurrently. Document that extension authors must handle that concurrency.

5. afterTool hooks receive the settled execution outcome and may transform bounded model-facing content/details and error presentation. They run for executed success/error results, not a beforeTool denial or a call cancelled before execution.

6. If afterTool fails after a side effect, return one actionable error indicating that execution already occurred and its effect may have applied; preserve execution status/details for inspection and never rerun the tool.

7. Propagate cancellation, bound hook-result content, keep source-order durable results and isolate sibling calls. A hook cannot drop a result, invent a different call ID or mark an unfinished call successful.

## Scope boundary

beforeTool and afterTool only. This enables an extension to implement policy; it does not add a built-in permission framework or sandbox.

## Implementation constraints

- Use Bun and TypeScript. Run `bun run typecheck`; run `bun test` for behavior changes. Deterministic checks use scripted models, protocol fixtures and temporary filesystems rather than paid APIs.
- Schway owns the loop, session engine, context/compaction and tool scheduling. Provider SDKs are protocol clients with automatic retries disabled; core contracts use native conversation types.
- Keep core independent of OpenTUI and provider wire types. Headless execution must not load the TUI; only selected providers and explicitly enabled executable extensions load.
- Resolve tool-relative paths from the canonical primary workspace root (nearest Git root, otherwise launch cwd). Keep runtime events separate from durable semantic session records.
- Document newly exported functions/types with a one-line TSDoc contract. Preserve bounded model-facing output, exactly one result per accepted call and existing credential redaction.

## Verification scenarios

| Scenario | Observable result |
| --- | --- |
| Allowed mutation | Rewritten valid arguments reach a real temporary-file edit. |
| Invalid mutation/denial | No file changes occur; exactly one error result is persisted. |
| After-side-effect failure | File changed once; result explains the post-execution hook failure; no replay. |
| Parallel siblings/exclusive barrier | A hook failure does not discard successful sibling results or violate ordering. |
| Cancellation | Queued/running calls settle once and no unchecked work begins after cancellation. |

## Acceptance criteria

- [ ] Validate model arguments before beforeTool and validate resulting arguments again before executing.
- [ ] Apply hooks in load order; invalid mutations, denials and beforeTool failures produce exactly one bounded error result without running the unchecked tool.
- [ ] Define afterTool supported result changes and failure behavior; never replay a completed side effect.
- [ ] Preserve scheduler barriers, source-order durable results, sibling results, cancellation and bounded model content.
- [ ] Real-loop tests use a real temporary file mutation and multiple hooks to prove allowed/denied/invalid/error paths and afterTool failure recovery.
- [ ] All required behavior and verification scenarios above are covered, including failure/cancellation cases relevant to this slice.
- [ ] User-facing commands/configuration and public contracts introduced by this issue are documented with a runnable example where applicable.
