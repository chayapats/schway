## What to build

Enabled extensions add discoverable interactive commands and observe the same runtime events used by headless JSON and the TUI.

## Existing behavior and problem

Explicitly enabled extensions already initialize in a deterministic order and can register custom tools atomically. The TUI currently dispatches fixed built-in slash commands. Runtime events already drive the TUI and headless JSON stream but are not exposed as an isolated extension observation service.

## Prerequisite contract

Requires the explicit extension runtime, source identity, atomic registration and disposal boundary from local extension loading. Existing RuntimeEvent is the canonical event union; additions must serve all consumers.

## Required behavior and decisions

1. Extend the public registration context with command registration and runtime-event subscription. Commands declare a name, help description and argument handling; show them in /help and dispatch from the same input editor.

2. Reserve built-in names. Reject conflicts between extension commands and discovered skill commands or other extension commands with both source identities. Registration order must not silently change which command runs.

3. Run registered commands only while the controller is idle; during an active turn show a busy diagnostic and retain input. Command execution can return display text or submit a normal user prompt through a supported controller capability; it cannot take ownership of the loop.

4. Commands that throw produce a source-labelled diagnostic and restore usable editor state. Cancellation and disposal must stop owned asynchronous work through the supplied signal.

5. Observers receive read-only notifications using the existing normalized runtime vocabulary. Protect agent/session state from listener mutation and catch synchronous throws and asynchronous rejections per listener.

6. Observer work must not gate model/tool completion. Preserve delivery order for each listener, bound any queue, and report dropped notifications explicitly if the configured bound is exceeded; authoritative runtime output and durable results remain intact.

7. Return unsubscribe/disposal handles and invoke them when the extension runtime is disposed. Session replacement must not multiply subscriptions or retain handlers for a destroyed controller.

## Scope boundary

Command registration and observation only. Listeners are not intervention hooks, and extension commands do not create a workflow engine.

## Implementation constraints

- Use Bun and TypeScript. Run `bun run typecheck`; run `bun test` for behavior changes. Deterministic checks use scripted models, protocol fixtures and temporary filesystems rather than paid APIs.
- Schway owns the loop, session engine, context/compaction and tool scheduling. Provider SDKs are protocol clients with automatic retries disabled; core contracts use native conversation types.
- Keep core independent of OpenTUI and provider wire types. Headless execution must not load the TUI; only selected providers and explicitly enabled executable extensions load.
- Resolve tool-relative paths from the canonical primary workspace root (nearest Git root, otherwise launch cwd). Keep runtime events separate from durable semantic session records.
- Document newly exported functions/types with a one-line TSDoc contract. Preserve bounded model-facing output, exactly one result per accepted call and existing credential redaction.

## Verification scenarios

| Scenario | Observable result |
| --- | --- |
| Command invocation | Custom help entry and arguments work; submitted prompts use the real controller/loop. |
| Collisions/busy state | Core, skill and extension conflicts are reported; a busy command never mutates an active run. |
| Bad observer | Throw, reject and attempted event mutation do not affect sibling listeners or agent results. |
| Ordering/cleanup | Per-listener event order is stable; switching/new sessions does not duplicate notifications. |
| Headless parity | Observers see native events while stdout remains valid runtime JSONL. |

## Acceptance criteria

- [ ] Extension commands appear in help and execute from the input editor; define deterministic collisions with built-ins, skills and other extensions.
- [ ] Expose read-only runtime-event subscriptions with deterministic subscription/disposal behavior across new/resumed sessions.
- [ ] Observer exceptions are reported with extension identity and cannot alter events, discard tool results or abort the agent.
- [ ] Command failures are actionable and leave the editor usable; cancellation and busy-state rules are explicit.
- [ ] Controller and real-loop tests use a command plus observer fixture and verify event parity, isolation, collision handling and cleanup.
- [ ] All required behavior and verification scenarios above are covered, including failure/cancellation cases relevant to this slice.
- [ ] User-facing commands/configuration and public contracts introduced by this issue are documented with a runnable example where applicable.
