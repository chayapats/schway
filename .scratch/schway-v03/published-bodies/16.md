## What to build

Users select off/low/medium/high reasoning controls, with truthful per-provider capability handling and settings visible in the TUI. Scope: sections 16–17, 91.

## Existing behavior and problem

The native conversation representation already preserves thinking content and opaque metadata. The catalog has capability metadata, but the public model request/settings do not offer a user-facing reasoning level. Add an explicit off/low/medium/high setting without assuming providers use equivalent wire controls.

## Prerequisite contract

No blockers. Reuse current config validation, catalog fallback, adapter boundary and controller model switching; later subscription integration uses the same native setting if its verified transport supports it.

## Required behavior and decisions

1. Expose a validated thinking level through configuration, --thinking on the CLI and /thinking in interactive mode; display requested and effective values with the active provider/model. Current-session choice follows ordinary override precedence.

2. Use a provider-independent level in harness-facing contracts and map it at adapter construction/request conversion. Provider field names, budgets and special metadata stay within their adapter.

3. Use current official provider documentation when implementing each mapping. Record which models support disabling reasoning, numeric budgets or named effort levels; unsupported values produce a clear pre-request error or disabled picker entry.

4. Unknown model IDs remain usable. If support cannot be established, leave provider defaults untouched when no explicit level is requested, and explain an unsupported explicit request instead of pretending it applied.

5. Native adapters must satisfy model-specific output/reasoning budget constraints. Compatible endpoints opt into documented mapping/capability configuration; do not blindly inject one vendor's effort field into every server.

6. Define a single source of truth when compatible extra-body values also configure reasoning: conflicting explicit controls are rejected with the conflicting setting names, rather than silently applying one.

7. Keep thinking/opaque metadata round trips working across tool calls, compaction and resume. Changing reasoning affects future model requests and does not rewrite historical messages.

8. Model/profile changes recompute capability and effective reasoning. A requested setting that becomes unsupported prevents the switch or asks for an explicit compatible value through the normal UI error path; no silent dishonest display.

## Scope boundary

User-level reasoning controls and truthful capability handling. No provider-specific wire types in core, new model catalog service or speculative support for every custom model.

## Implementation constraints

- Use Bun and TypeScript. Run `bun run typecheck`; run `bun test` for behavior changes. Deterministic checks use scripted models, protocol fixtures and temporary filesystems rather than paid APIs.
- Schway owns the loop, session engine, context/compaction and tool scheduling. Provider SDKs are protocol clients with automatic retries disabled; core contracts use native conversation types.
- Keep core independent of OpenTUI and provider wire types. Headless execution must not load the TUI; only selected providers and explicitly enabled executable extensions load.
- Resolve tool-relative paths from the canonical primary workspace root (nearest Git root, otherwise launch cwd). Keep runtime events separate from durable semantic session records.
- Document newly exported functions/types with a one-line TSDoc contract. Preserve bounded model-facing output, exactly one result per accepted call and existing credential redaction.
