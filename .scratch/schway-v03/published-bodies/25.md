## What to build

Maintainers compare coding reliability across supported providers on multi-file, search, failure recovery, long-context and parallel-read tasks.

## Existing behavior and problem

The prerequisite runner already creates isolated repositories, executes a bounded real Schway run, grades environment outcomes, and reports tool/retry/compaction/token metrics with unknown usage represented honestly. Expand its case library; do not build another runner or grader framework.

## Prerequisite contract

Consumes the existing eval case/runner/grader interfaces and result artifact containing outcome, wall time, normalized known/unknown usage, tool calls/failures, retries, compactions and duplicate-call counts.

## Required behavior and decisions

1. Add a multi-file refactor case with coupled definitions/callers and tests that fail if only one file changes or behavior regresses.

2. Add a locate-implementation case with plausible distractors and a machine-checkable answer artifact referencing the correct implementation; prose confidence alone is not a grade.

3. Add a failing-tests case where the agent must diagnose and repair a real failing behavior rather than delete/disable the tests. The grader checks test integrity and actual expected behavior.

4. Add a long-context case with constraints and key facts in older complete turns, enough pressure to exercise real compaction, and a final task that fails if those facts are lost.

5. Add a tool-error-recovery case with a recoverable invalid/missing target followed by a valid path; grade the eventual environment outcome and capture the error metrics.

6. Add a parallel-read case that offers multiple independent required inputs, grades use of their content and records execution overlap in controlled fixtures. Do not score a real model solely on wall-clock timing.

7. For each case define seeded state, task, bounds, grader, positive fixture and representative false-positive/negative fixtures. Keep fixtures small enough for repeatable local runs.

8. Support a selected provider/model matrix with comparable case/config metadata and per-case outcomes. Skip unavailable providers explicitly; collect empirical baselines before claiming reliability thresholds.

9. Report both success and resource/call metrics through the established artifact shape. Preserve raw bounded evidence needed to diagnose a failing grader without embedding secrets.

## Scope boundary

Six additional coding scenarios and comparative reporting. No leaderboard claims, open-ended benchmark collection or default paid CI.

## Implementation constraints

- Use Bun and TypeScript. Run `bun run typecheck`; run `bun test` for behavior changes. Deterministic checks use scripted models, protocol fixtures and temporary filesystems rather than paid APIs.
- Schway owns the loop, session engine, context/compaction and tool scheduling. Provider SDKs are protocol clients with automatic retries disabled; core contracts use native conversation types.
- Keep core independent of OpenTUI and provider wire types. Headless execution must not load the TUI; only selected providers and explicitly enabled executable extensions load.
- Resolve tool-relative paths from the canonical primary workspace root (nearest Git root, otherwise launch cwd). Keep runtime events separate from durable semantic session records.
- Document newly exported functions/types with a one-line TSDoc contract. Preserve bounded model-facing output, exactly one result per accepted call and existing credential redaction.

## Verification scenarios

| Scenario | Observable result |
| --- | --- |
| Every grader | At least one correct solution and meaningful wrong solution demonstrate that the grader can go green and red. |
| Offline suite | Scripted cases exercise each scenario through the real runner without paid APIs. |
| Long context | The test actually creates compaction and proves retained task facts influence the final graded result. |
| Matrix/status | Mixed pass/fail/skipped providers aggregate correctly without treating missing evidence as success. |
| Repeatability | Repeated runs from the same seeded state use isolated repositories and preserve source fixtures. |
