## What to build

Users explicitly save or remove provider credentials and later run Schway without re-entering keys, using the operating system's secure storage. Scope: sections 63–64, 72–73, 91.

## Existing behavior and problem

API-key resolution currently supports only explicit runtime values and environment variables. Keys are rejected from ordinary configuration. Introduce a third, lower-priority credential source backed by OS-native storage, while preserving deterministic headless behavior and optional/no-auth compatible endpoints.

## Prerequisite contract

No blockers. Reuse existing credential precedence, provider loading and redaction. Export a narrow storage boundary that later subscription auth can use without importing OS details into core.

## Required behavior and decisions

1. Add a credential-store boundary with get/set/delete operations keyed by provider credential identity. Use Bun's available OS-native secure storage behind it; tests inject a fake store and never touch the developer's actual keychain.

2. Resolve credentials in this order: explicit runtime override, environment, secure stored value, missing. An explicitly supplied empty override is an error, not a request to fall back. Read the secure store only if a higher-priority usable source is absent.

3. Provide interactive /login <provider> for masked API-key entry and /logout <provider> to delete that stored credential. Distinguish stored, environment and runtime sources so logout does not claim to remove an environment variable.

4. Derive compatible-provider credential identity from a canonical endpoint or named profile when profiles exist. Native Anthropic/OpenAI identities stay separate. Never reuse a credential across unrelated endpoints by accident.

5. Unavailable, locked or denied secure storage produces an actionable error for save/read/delete. Do not silently fall back to plaintext files. A valid runtime/environment credential remains usable even if the store is unavailable.

6. Keep secret input out of transcript, command recall, configuration, session records and runtime/debug output. Failed/cancelled entry stores nothing; overwrite/delete acts only on the explicitly selected identity.

7. Headless execution may consume existing stored credentials but never initiates interactive login. Optional/none compatible auth continues to work according to its configured mode.

8. Document platform requirements and an opt-in native-store smoke procedure. Do not claim all supported OS stores passed based on a fake-store test.

## Scope boundary

API keys and secure-store infrastructure. Browser/device OAuth and subscription transport are handled separately; no automatic migration from another CLI.

## Implementation constraints

- Use Bun and TypeScript. Run `bun run typecheck`; run `bun test` for behavior changes. Deterministic checks use scripted models, protocol fixtures and temporary filesystems rather than paid APIs.
- Schway owns the loop, session engine, context/compaction and tool scheduling. Provider SDKs are protocol clients with automatic retries disabled; core contracts use native conversation types.
- Keep core independent of OpenTUI and provider wire types. Headless execution must not load the TUI; only selected providers and explicitly enabled executable extensions load.
- Resolve tool-relative paths from the canonical primary workspace root (nearest Git root, otherwise launch cwd). Keep runtime events separate from durable semantic session records.
- Document newly exported functions/types with a one-line TSDoc contract. Preserve bounded model-facing output, exactly one result per accepted call and existing credential redaction.

## Verification scenarios

| Scenario | Observable result |
| --- | --- |
| Resolution | Runtime beats env, env beats stored, stored beats missing; explicit empty values error. |
| Store failures | Locked/unavailable store yields clear errors only when needed, without plaintext fallback. |
| Lifecycle | Masked login, cancelled login, overwrite, logout and missing identity have deterministic outcomes. |
| Provider use | A resolved fake-store key reaches the intended provider constructor and no other identity. |
| Secret handling | Transcript, JSONL, config and diagnostics contain no injected sentinel secret. |

## Acceptance criteria

- [ ] Add explicit interactive credential login/logout management with masked input and provider identity.
- [ ] Credential resolution is runtime override, environment, secure storage, then actionable missing credential; headless never starts a login flow.
- [ ] Use Bun-supported OS storage behind an injectable boundary; unavailable/locked stores produce clear recovery guidance without plaintext fallback.
- [ ] Never write keys to normal config, session JSONL, logs, command history or display output; deletion targets only the selected credential.
- [ ] Deterministic tests use a fake store and verify actual provider construction, precedence, save/read/delete, cancellation and store failures; native-store smoke checks are opt-in.
- [ ] All required behavior and verification scenarios above are covered, including failure/cancellation cases relevant to this slice.
- [ ] User-facing commands/configuration and public contracts introduced by this issue are documented with a runnable example where applicable.
