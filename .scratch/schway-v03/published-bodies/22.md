## What to build

Users run schway doctor to see actionable health information about the installed runtime, workspace, providers and optional capabilities without starting a model conversation.

## Existing behavior and problem

The prerequisites provide configured skill/extension manifests, secure credential identities, named compatible profiles and verified subscription authentication. Existing workspace/configuration/provider/tool/session code already knows the remaining health facts. doctor must aggregate them without starting a model run or requiring valid credentials merely to diagnose missing credentials.

## Prerequisite contract

Requires read-only manifest/skill discovery, profile resolution, credential-source/status inspection and isolated subscription auth status. Each returns data or structured errors without model construction; the needed contracts are specified here.

## Required behavior and decisions

1. Implement schway doctor as a dedicated diagnostic command that can run before ordinary provider construction and TUI initialization. It must remain usable when configuration is partially invalid.

2. Report Schway version, Bun/runtime and platform; primary workspace and Git availability; shell/search backend availability; session-directory existence/access. Classify each check as ok, warning or error with a concrete remedy.

3. Report selected provider/profile, effective auth source category and whether the necessary credential/store is available. Check presence/status only; never print credential values or open browser login.

4. Include secure-store unavailable/locked, unknown profile, malformed configuration, missing subscription login and known expiry/refresh requirements where they can be determined locally. External connectivity/live model checks are out of scope.

5. Inspect skill metadata and explicitly configured package/extension manifests using read-only discovery. Report duplicates, missing entries and invalid manifests without executing arbitrary extension registration code.

6. Offer readable default output and stable structured output for automation. Use exit 0 when no required check fails, exit 1 for diagnosed required failures and exit 2 only if doctor itself cannot complete; warnings alone do not fail.

7. Distinguish optional disabled capability from broken enabled capability. Missing credentials are an error only for the selected auth/provider mode that requires them; unauthenticated compatible endpoints can be healthy.

8. Make checks independently reportable so one invalid config/manifest or store error does not suppress unrelated runtime/workspace findings. Bound captured subprocess output and redact all errors.

## Scope boundary

Local readiness diagnostics. No automatic repair, package installation, network health probing or live provider calls.

## Implementation constraints

- Use Bun and TypeScript. Run `bun run typecheck`; run `bun test` for behavior changes. Deterministic checks use scripted models, protocol fixtures and temporary filesystems rather than paid APIs.
- Schway owns the loop, session engine, context/compaction and tool scheduling. Provider SDKs are protocol clients with automatic retries disabled; core contracts use native conversation types.
- Keep core independent of OpenTUI and provider wire types. Headless execution must not load the TUI; only selected providers and explicitly enabled executable extensions load.
- Resolve tool-relative paths from the canonical primary workspace root (nearest Git root, otherwise launch cwd). Keep runtime events separate from durable semantic session records.
- Document newly exported functions/types with a one-line TSDoc contract. Preserve bounded model-facing output, exactly one result per accepted call and existing credential redaction.

## Verification scenarios

| Scenario | Observable result |
| --- | --- |
| Installed entry | The packed executable runs doctor without loading TUI or making model requests. |
| Broken installation | Missing search backend and inaccessible session storage produce remedies and failure status. |
| Config/manifest failure | Multiple independent issues remain visible even when one source is malformed. |
| Auth variants | API-key presence, optional/none auth, locked store, profile and subscription states are reported safely. |
| Read-only inspection | An extension module with a side-effect marker is not executed; no login or credential mutation occurs. |
