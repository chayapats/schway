# Keep remembered interactive choices separate from explicit configuration

The user approved remembering the last successfully activated interactive model/auth choice per canonical primary workspace, below explicit user/project/CLI configuration and above built-in defaults. Existing workspaces retain their own choices. A workspace with no memory record inherits the latest successfully remembered eligible choice across workspaces, including provider, model, auth route and reasoning as one tuple. Starting or resuming a session does not write either record. Headless execution ignores both records, and explicit credential/billing precedence remains authoritative.

Credential persistence, remembered model selection, and durable conversation history are separate state. Explicit resume resolves the resumed workspace's current effective settings rather than silently restoring an old billing route from conversation history. Failed or cancelled activation, startup and resume never publish a new remembered choice.

Global inheritance deliberately excludes compatible endpoints and profiles, even if currently defined in user configuration, and any selection with an explicit endpoint URL. A profile name alone cannot establish the same connection in another project: project definitions can replace user definitions and bind that name to a different endpoint. These choices remain workspace-only; they neither copy endpoint details nor replace the last eligible global choice. Legacy xAI choices without an explicit auth route remain readable locally but are not eligible for global publication.

Version 1 workspace records remain authoritative without migration writes. An empty reset/forget record suppresses global fallback, and malformed workspace state blocks fallback instead of silently choosing another billing route. Malformed global state affects only workspaces without a record; a successful eligible selection repairs it. Forgetting creates only a local reset record, leaving other workspaces and the global choice intact.

Each JSON record is replaced atomically under a retained SQLite process lock. Workspace revision checks reject stale writers; a separate shared lock serializes global publication across workspaces. Both files are staged before the workspace rename, which is the local commit point. The global rename follows. These two files are not one filesystem transaction: if global publication fails or the process exits between renames, the workspace can retain the new choice while new workspaces retain the previous fallback. On a reported publication failure the editor adopts the committed workspace revision and explains that selection can be retried. This preserves local continuity and retryability without pretending the global write succeeded. No credentials, endpoint URLs, headers or conversation text enter either record.
