# Local diagnostics

Schway does not write diagnostic logs unless you opt in. To investigate a run:

```bash
schway -p "explain this project" --json --debug
# Or choose a local file (relative to launch cwd):
schway -p "explain this project" --debug-file ./schway-debug.jsonl
# For an interactive session:
schway --debug
```

`--debug` writes newline-delimited JSON records to `~/.schway/logs/diagnostics.jsonl` (`HOME` determines `~`). `--debug-file <path>` enables logging and overrides that destination. Keep explicit destinations private; the default directory and file are created with owner-only permissions (0700/0600). Pre-existing non-private default log directories and any non-private destination files, final-file symlinks and hard-linked destination files are refused rather than chmodded or altered. Destinations inside `~/.schway/sessions` (including canonical/symlink aliases) are refused before writing or rotation; a diagnostic path cannot be a durable session file. There is no upload, collection endpoint or verbose/raw-payload mode.

Each record has `timestamp` (ISO 8601), `level`, `runId` (unique invocation identifier), `sessionId` (null until a session is ready), `component`, `event`, and bounded `fields`. Diagnostics include startup/provider configuration identifiers and limits, retry categories/attempts/delays, safe failure categories (not provider error messages), tool names/IDs/status, and compaction transitions. Prompt contents, streamed text, tool arguments, tool output/details, provider payloads and full conversation history are **not** logged. Sensitive structured keys (including auth/signature, authentication headers, tokens, passwords and credentials) are excluded; Error names/messages are replaced by a fixed category, and known runtime secrets, bearer/basic credentials and URL userinfo/query credentials across URL schemes are masked in remaining strings. Avoid placing arbitrary secrets inside non-credential identifiers. Logs are locally sensitive metadata and should not be shared without inspection.

The active file is limited to 1 MiB with three retained archives (`diagnostics.jsonl.1` through `.3`, oldest discarded). Each line is bounded to under 4 KiB, oversized field values/identifiers are replaced before text processing rather than cut through a credential, and the in-memory pending queue is limited to 128 records. Excess entries and individual records exceeding the configured file-size limit are dropped, not allowed to delay the agent. Pre-existing oversized active files or archives are refused without truncating or rotating them. Filesystem errors disable that invocation's logging; they never fail a model/tool run. During orderly exit or cancellation, Schway waits up to 1.5 seconds for pending writes, then proceeds. Interactive quit with an active operation logs `tui.shutdown` / `cancellation_requested` before disposal; it does not claim `agent.finished` unless the loop actually settled. Avoid writing to remote or slow filesystems if you need reliable final diagnostics.

Headless `--json` continues to print normalized runtime events on stdout and the existing `~/.schway/sessions/*.jsonl` files continue to hold only durable semantic conversation records. The diagnostic file is neither an archive of prompts nor a replacement for session state.

Internal consumers can use `createDiagnosticSink({ home, enabled, runId, sessionId, secrets })` from `src/diagnostics/sink.ts`: call `record(component, event, fields, level)` with metadata only or `runtime(event)` with a normalized runtime event, then `close()` at shutdown. Interactive `TuiControllerOptions.onRuntimeEvent(event, sessionId)` is an optional current-turn observer with a lightweight active session ID, invoked before display folding; throws and rejected promises are ignored so the turn and durable tool results still settle. Schway only supplies it when `--debug` is enabled. Automatic compaction is observed through native events; interactive `/compact` emits the same callback vocabulary (`started` then `completed` with IDs, `noop` on no result/cancellation, or `failed` on rejection). All fields and correlation identifiers pass through the common sanitizer before JSON serialization; do not pre-stringify potentially sensitive objects or log raw payloads. Runtime events project safe metadata only, and even arbitrary provider error/retry/compaction messages are never serialized.
